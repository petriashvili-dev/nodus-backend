# Синхронизация, идемпотентность и конфликты

Код: `Nodus.Api/Sync/`.

## Client → Server: идемпотентные мутации

Клиент работает офлайн-first: создаёт изменение локально, кладёт его в свой outbox и отправляет, когда есть сеть, повторяя при сбоях. Чтобы повторы были безопасны, **каждая мутация** несёт заголовок:

```http
Idempotency-Key: 7f6c1b0e-…    (1–128 символов, уникален в пределах пользователя)
```

Без него → `400 idempotency_key_required`. Исключения: `/v1/auth/*` (кроме email-привязки) и `/v1/devices` — они идемпотентны по смыслу.

| Ситуация | Ответ |
|---|---|
| Первый запрос | выполняется, ответ сохраняется в `client_operations` |
| Повтор с тем же ключом и тем же запросом | **тот же** код и тело байт в байт, заголовок `Idempotent-Replayed: true`, действие не повторяется |
| Тот же ключ, но другой запрос (метод, путь, query, тело) | `422 idempotency_key_reused` |
| Несколько одинаковых запросов одновременно | выполняется один, остальные получают его результат |
| Обработчик вернул 4xx | сохраняется и он: повтор получит ту же ошибку. Для новой попытки нужен новый ключ |

Ключи одного пользователя не пересекаются с ключами другого. Записи хранятся `Retention:IdempotencyDays` (30 дней) — это должно быть больше, чем клиент может держать неотправленный outbox.

### Пакетное создание

`POST /v1/nodes/batch` — одна транзакция, до 50 узлов, id генерирует клиент, ответ содержит узлы в порядке запроса. Ошибка в любом узле → `400` с полями вида `nodes[1].title`, ничего не создаётся.

## Версии и конфликты

У узла есть `version`, растущая при каждом изменении (включая состав участников).

```http
PATCH /v1/nodes/{id}
{ "expected_version": 3, "title": "…", … }
```

Если узел уже изменили (особенно актуально для совместных узлов):

```json
409 { "code": "version_conflict", "current": { …каноническое состояние узла… } }
```

Клиент сохраняет своё намерение, применяет `current` и разрешает конфликт явно (показывает пользователю или повторяет правку поверх новой версии). **Молчаливого last-write-wins для правок нет.**

Исключение — развязать/перевязать: это идемпотентные операции над состоянием, побеждает последняя.

Если конфликт пойман уже на уровне БД (гонка), ответ — `409 version_conflict` без `current`; клиент синхронизируется и повторяет.

## Server → Client: журнал изменений

Каждое изменение сущности записывается в `sync_changes` **для каждого получателя** (владелец, участники, сам пользователь):

| Поле | Значение |
|---|---|
| `recipient_user_id`, `revision` | монотонная ревизия получателя, без пропусков |
| `entity_type` | `user`, `node`, `occurrence_state`, `connection`, `ai_draft_job`, `suggestion` |
| `entity_id`, `operation`, `entity_version` | что изменилось: `upsert` / `delete` |

**Как обеспечена монотонность.** Ревизия выделяется из `users.sync_revision` через `UPDATE … RETURNING` внутри транзакции мутации. Это блокирует строку получателя до коммита, поэтому изменения одного получателя видны строго в порядке ревизий: читатель с курсором N не может «проскочить» изменение с ревизией ≤ N, закоммиченное позже. Для изменений с несколькими получателями строки блокируются в порядке id, чтобы не было взаимных блокировок.

Журнал хранит только **ссылки**. Сами данные берутся в момент чтения, поэтому клиент всегда получает актуальное каноническое состояние.

## Delta Sync

```http
GET /v1/sync?cursor=42&limit=200
```
```json
{
  "changes": [
    { "revision": 43, "entity_type": "node", "entity_id": "…", "operation": "upsert", "version": 5, "data": { …NodeDto… } },
    { "revision": 45, "entity_type": "node", "entity_id": "…", "operation": "delete", "version": 6, "data": null }
  ],
  "next_cursor": 45,
  "has_more": false
}
```

- Изменения в порядке ревизий; если сущность менялась несколько раз в пределах страницы — она приходит **один раз** с последней ревизией и текущими данными.
- `delete` (tombstone) приходит, если сущность удалена **или стала недоступна** (например, вас убрали из участников).
- Доступ проверяется при чтении: чужие узлы не попадают в ответ, даже если запись в журнале есть.
- Клиент применяет страницу и сохраняет `next_cursor` **атомарно**, затем продолжает, пока `has_more`.
- `limit` 1–1000, по умолчанию 200. Первый вызов — `cursor=0`.

### Когда синхронизироваться

На запуске, при возврате в foreground, при восстановлении сети, после успешной отправки outbox, по SSE-сигналу или push, при смене календарного дня.

## Устаревший курсор и snapshot

Журнал хранится `Retention:SyncChangeDays` (90 дней). Если курсор старше удалённой части (или вообще невалиден):

```json
410 { "code": "cursor_expired", "snapshot_url": "/v1/sync/snapshot" }
```

```http
GET /v1/sync/snapshot
```
```json
{
  "cursor": 1234,
  "user": { … }, "nodes": [ … ], "connections": [ … ],
  "ai_draft_jobs": [ … ], "suggestions": [ … ], "occurrence_states": [ … ]
}
```

Snapshot читается в одной транзакции `REPEATABLE READ`, `cursor` согласован с данными — дальше Delta Sync продолжается с него. Клиент заменяет локальные данные **не стирая свой неотправленный outbox**.

## Что приходит в `data`

| `entity_type` | `data` |
|---|---|
| `user` | профиль (`id`, `is_anonymous`, `email`, `display_name`, `version`) |
| `node` | `NodeDto` с участниками и экземплярами на горизонт |
| `occurrence_state` | `{ node_id, key, state, completed_at, version, … snapshot }`; `entity_id` = `{nodeId}:{key}` |
| `connection` | связь с точки зрения получателя (`user_id` — другой человек) |
| `ai_draft_job` | задание и черновики (без исходного текста) |
| `suggestion` | предложение продолжения |
