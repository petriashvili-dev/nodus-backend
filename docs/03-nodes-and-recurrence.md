# Узлы, повторения и экземпляры

Код: `Nodus.Api/Nodes/`, `Nodus.Api/Recurrence/`, `Nodus.Api/Occurrences/`.

## Типы узлов

| Тип | Поля | Экземпляры |
|---|---|---|
| `one_time` | `date?`, `time?` (без даты — «когда-нибудь», без времени — на весь день) | один, ключ `once` |
| `recurring` | `recurrence` (даты и времена внутри правила) | по правилу |
| `anniversary` | `date` — исходная дата события, `time?`, `track_years` | ежегодно; правило строится сервером из даты |

Общие поля: `id` (UUID, генерирует **клиент**, чтобы офлайн-созданный узел сохранял идентичность), `title` (≤ 200), `description?` (≤ 4000), `timezone` (IANA, например `Europe/Moscow`), `version`, `owner_id`, `members`.

## API

| Запрос | Что делает |
|---|---|
| `POST /v1/nodes` | создать узел |
| `POST /v1/nodes/batch` `{ nodes: [...] }` | создать до 50 узлов атомарно: либо все, либо ни одного |
| `GET /v1/nodes/{id}` | узел с экземплярами на горизонт |
| `PATCH /v1/nodes/{id}` | изменить шаблон: **полный** набор редактируемых полей + `expected_version` |
| `DELETE /v1/nodes/{id}?expected_version=` | мягкое удаление (только владелец) |
| `PUT /v1/nodes/{id}/occurrences/{key}/untie` `{ completed_at? }` | развязать экземпляр |
| `PUT /v1/nodes/{id}/occurrences/{key}/retie` | перевязать экземпляр |
| `GET /v1/nodes/{id}/occurrences?from&to` | история и будущее узла (до 400 дней) |
| `GET /v1/feed?from&to` | главная лента |
| `GET /v1/occurrences?from&to` | все экземпляры всех узлов на окно до 120 дней (локальные уведомления) |

Все мутации требуют `Idempotency-Key`, см. [04](04-sync-and-idempotency.md).

**Почему PATCH принимает полный шаблон:** у офлайн-клиента всегда есть узел целиком; так нет двусмысленности «поле очищено или не передано», а конфликт ловится по `expected_version`. Смена типа узла не поддерживается.

## Правило повторения

Собственная строгая схема (не RRULE), `Recurrence/RecurrenceRule.cs`:

```json
{
  "frequency": "weekly",          // daily | weekly | monthly | yearly
  "interval": 2,                  // каждые 2 недели (1–366)
  "start_date": "2026-10-01",
  "until": "2027-06-30",          // включительно, необязательно
  "times": ["07:30", "21:00"],    // до 12 раз в день; пусто = на весь день
  "week_days": ["monday", "friday"],  // только weekly; пусто = день недели start_date
  "month_day": 31                 // только monthly; пусто = день из start_date
}
```

Календарные правила (`RecurrenceCalculator.cs`):

- интервал считается от `start_date` (для weekly — по ISO-неделям, с понедельника);
- `month_day: 31` → последний день короткого месяца (28/29/30);
- ежегодное 29 февраля → 28 февраля в невисокосный год;
- время округляется до минут, списки сортируются и очищаются от дублей.

## Часовые пояса и DST

`Recurrence/ZonedTime.cs`. Принимаются только IANA-зоны. Политика:

| Ситуация | Пример (Berlin) | Результат |
|---|---|---|
| Обычное время | 09:00 | по текущему смещению |
| Время «выпало» при переводе вперёд | 29.03 02:30 (02:00→03:00) | сдвиг вперёд на длину разрыва → **03:30** |
| Время повторяется при переводе назад | 25.10 02:30 (03:00→02:00) | **более раннее** из двух (00:30 UTC) |

Ежедневное «в 09:00» остаётся 09:00 по местному времени через переход (между соседними днями может быть 23 или 25 часов).

## Экземпляры и их ключи

Регулярный узел хранится как **один шаблон**; экземпляры вычисляются. У каждого экземпляра стабильный ключ, **не зависящий от отображаемого времени**:

```
g{generation}-{yyyyMMdd}-{slot}      например g0-20261017-0
once                                 одноразовый узел
```

- `yyyyMMdd` — календарная дата по правилу;
- `slot` — позиция времени в `times` (0 для одного времени или «весь день»);
- `generation` — поколение серии. Увеличивается, только когда меняется **частота** (daily → weekly и т. п.), чтобы ключи новой серии не совпали со старыми.

Поэтому перенос времени 09:00 → 08:00 сохраняет ключ и состояние «развязано» у сегодняшнего экземпляра.

Ответ по экземпляру (`OccurrenceDto`):

```json
{
  "node_id": "…", "key": "g0-20261017-0", "revision": 1,
  "title": "Зарядка", "description": null,
  "date": "2026-10-17", "time": "09:00", "scheduled_at": "2026-10-17T06:00:00+00:00",
  "years": null, "state": "untied", "completed_at": "…", "is_past": true
}
```

## Развязать / перевязать

- Действует **только на один экземпляр**, остальные не меняются.
- Неизвестный ключ (такого экземпляра нет у узла) → `404 occurrence_not_found`.
- Повтор того же состояния — no-op (`200`, версия не меняется), поэтому повторы безопасны.
- `completed_at` от клиента принимается, если он не в будущем и не старше `Occurrences:MaxCompletionBackdateDays` (30 дней) — так офлайн-развязывание сохраняет реальное время; иначе берётся время сервера.
- Состояние хранится в `node_occurrence_states` вместе со **snapshot** экземпляра на момент действия (ревизия, название, дата, время).
- Развязать можно и будущий экземпляр (сделано заранее).

## История правок

Требование: «прошлые экземпляры не меняются после глобальной правки». Пересчётом по текущему правилу этого не добиться, поэтому:

1. Каждая правка регулярного/ежегодного узла добавляет неизменяемую запись в `node_revisions` с моментом вступления `effective_from = now` (у первой ревизии — без нижней границы).
2. `RecurrenceProjectionService` при построении экземпляров **проигрывает** ревизии по порядку.

Правило принадлежности экземпляра ревизии:

> Экземпляр принадлежит ревизии `i`, если он **уже был в прошлом**, когда вступила ревизия `i+1`. Иначе — более поздней ревизии.
> «В прошлом» для экземпляра со временем — его момент; для экземпляра «на весь день» — конец его дня.
> Поздняя ревизия не создаёт экземпляров в датах **раньше дня своего вступления**.
> Ключ, однажды закреплённый за ревизией, позже не порождается повторно.

Примеры (правка сегодня в 10:00):

| Было → стало | Вчера | Сегодня | Завтра |
|---|---|---|---|
| «Зарядка» 09:00 → «Утренняя зарядка» 08:00 | старое | старое (09:00 уже прошло) | новое 08:00 |
| 20:00 → 09:00 | старое | новое 09:00 (сегодняшнее ещё не наступило по старому правилу) | новое |
| пн → пн+вт | — | вторник в прошлом не появляется | новое |
| правило заканчивается вчера (`until`) | история и состояния сохраняются | — | — |

Результат детерминирован, поэтому не нужна ежедневная «материализация» прошлого, и пропущенный запуск задачи ничего не ломает.

## Лента и горизонт

- `GET /v1/feed` — проекция главного экрана: одноразовые узлы с датой в `[from, to]` и узлы без даты; для каждого регулярного/ежегодного — **сегодняшние экземпляры + ближайший следующий** (если сегодня ничего нет — только ближайший будущий). «Сегодня» считается в зоне узла. Клиент перезапрашивает ленту при смене дня, даже если ничего не правилось.
- Каждый `NodeDto` содержит `horizon` и `occurrences` — готовые экземпляры от вчера до `Occurrences:HorizonDays` (45) дней вперёд, чтобы iOS планировала локальные уведомления без сети.
- Прошедший невыполненный экземпляр сервер отдаёт с `is_past: true, state: "tied"`; показывать ли его как просроченный — решает клиент.

## Удаление

`DELETE` — мягкое: `deleted_at`, узел пропадает из ленты, получатели в sync видят tombstone (`operation: delete`). Ревизии и состояния экземпляров остаются в БД. Удалять может только владелец.
