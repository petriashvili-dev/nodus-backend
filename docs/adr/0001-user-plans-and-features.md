# 0001. Планы пользователей и доступ к функциям

Дата: 2026-10-18 · Статус: принято

Как это работает в коде — [11-plans-and-features.md](../11-plans-and-features.md).

## Контекст

Часть функций должна быть доступна не всем пользователям. В первую очередь это всё, что вызывает LLM: каждый вызов стоит денег, а качество ещё проверяется на ограниченной группе.

| Функция | Ключ | Как запускается | Код |
|---|---|---|---|
| Голосовой разбор в черновики | `ai_drafts` | `POST /v1/ai/node-drafts` | `AiDrafts/` |
| «Продолжение нити» | `ai_continuations` | неявно: создание/смысловая правка одноразового узла → outbox `ai.continuation.requested` | `AiContinuations/` |
| AI-импорт чужого файла | `ai_import` | `POST /v1/me/import` с файлом не формата Nodus | `DataPortability/ImportService.cs` (`QueueAiImportAsync`) |

Сейчас есть только глобальный `AiContinuations:Enabled` и суточные лимиты (`Ai:MaxJobsPerDay`, `AiContinuations:MaxLlmCallsPerUserPerDay`, `Import:MaxAiImportsPerDay`); выключить функцию для конкретного пользователя нельзя.

Продуктовая модель: два плана — обычный и **Nodus+**. Сейчас Nodus+ выдаётся **вручную и бесплатно** группе тестирования; в приложении о подписке ничего не говорится, пользователь без доступа просто не видит функций. Позже Nodus+ может стать платным — **только** через In-App Purchase (App Review Guidelines 3.1.1). Для ревью: в App Review Notes указывается, что функции включаются на сервере для ограниченной группы, и даётся демо-аккаунт с Nodus+ (2.1, 2.3.1).

Инварианты:

- функцию с LLM нельзя запустить без доступа ни через API, ни неявно через фон;
- клиент заранее знает, какие функции ему доступны, и не показывает недоступные;
- потеря доступа не уничтожает уже полученные результаты пользователя;
- проверка доступа не зависит от того, откуда взялся план (вручную или App Store).

## Решение

### Модель данных

Три колонки в `users`:

| Колонка | Тип | Смысл |
|---|---|---|
| `plan` | `varchar(16) not null` | `Standard` \| `Plus` (check constraint `ck_users_plan`) |
| `plan_source` | `varchar(16) null` | `Manual`; позже `AppStore` |
| `plan_expires_at` | `timestamptz null` | `null` — бессрочно |
| `ai_consent_at` | `timestamptz null` | когда пользователь согласился на передачу данных AI-провайдеру; `null` — не соглашался или отозвал |

**Действующий план** = `plus`, если `plan = 'plus'` и (`plan_expires_at is null` или `plan_expires_at > now`), иначе `standard`. Считается при чтении через `TimeProvider`; фоновой задачи «истечения» нет.

### План → функции

Набор функций каждого плана — в конфигурации, а не в коде:

```json
"Plans": {
  "Standard": { "Features": [] },
  "Plus": { "Features": ["ai_drafts", "ai_continuations", "ai_import"] }
}
```

Так функцию можно открыть всем (добавить в `Standard`) без релиза кода. Ключи функций — закрытый список констант `Features` в `Plans/`; неизвестный ключ в конфигурации — ошибка валидации options при старте.

Сервис `FeatureAccess` (scoped):

- `IReadOnlySet<string> For(User user)` — функции действующего плана;
- `CheckAsync(userId, feature)` → `Allowed | NotInPlan | ConsentRequired` и `DenyAsync` → готовый `403` — с кешем на запрос (scoped), чтобы пакетные операции не делали N запросов.

### Согласие на передачу данных AI

App Review Guideline 5.1.2(i) требует явного согласия перед передачей персональных данных стороннему AI. «Продолжение нити» отправляет текст узла модели **на сервере, без действия пользователя**, поэтому согласие, хранящееся только на клиенте, не защищает: факт согласия хранится в `users.ai_consent_at` и проверяется сервером для **всех** AI-функций.

```http
PUT /v1/me/ai-consent      (Idempotency-Key)
{ "granted": true }
→ 200 UserProfile
```

`granted: false` обнуляет `ai_consent_at` (отзыв). Повтор с тем же значением не меняет время первого согласия и `version`. Изменение — через `UnitOfWork` с записью `SyncEntityType.User`.

Функция **доступна**, если она есть в плане **и** `ai_consent_at is not null`. Это одна проверка `FeatureAccess`, но с разными кодами отказа, чтобы клиент знал, что делать.

### Где проверяется доступ

| Функция | Проверка | Отказ |
|---|---|---|
| `ai_drafts` | endpoint filter `.RequireFeature(Features.AiDrafts)` на `POST /ai/node-drafts` — до идемпотентности и rate limit по AI | `403 feature_not_available` / `403 ai_consent_required` |
| `ai_import` | в `ImportService` **только в ветке AI** (`QueueAiImportAsync`, внутри идемпотентности — отказ сохраняется за ключом, как и `ai_quota_exceeded`); импорт файла Nodus доступен всем | `403 feature_not_available` / `403 ai_consent_required` |
| `ai_continuations` | 1) `ContinuationTrigger` не пишет outbox-событие, если у владельца узла нет функции или согласия; 2) `HardFilter` конвейера проверяет ещё раз — доступ или согласие могли пропасть за время debounce | молча: ничего не происходит |

Сначала проверяется план, потом согласие: пользователю без плана не нужно предлагать согласиться. Ответ отказа:

```json
{ "type": "...", "title": "Feature is not available.", "status": 403, "code": "feature_not_available", "feature": "ai_drafts" }
```

Код ошибки `ai_consent_required` использует то же тело и поле `feature`.

Узлы, созданные до согласия, задним числом в конвейер не отправляются: после согласия «Продолжение нити» работает для новых и изменённых узлов.

Не закрываются (только чтение и завершение уже начатого, без вызова LLM): `GET /ai/node-drafts`, `GET /ai/node-drafts/{id}`, `confirm`, `cancel`; `GET /me/imports/{id}`, `confirm`, `cancel`; `POST /suggestions/{id}/shown|accept|dismiss`. Задания, принятые до потери доступа, доходят до конца. Уже готовые предложения продолжения остаются.

### Контракт для клиента

`UserProfile` (`GET /v1/me`, сущность `user` в sync, ответы `PATCH /me`, `PUT /me/ai-consent` и `email/verify`) получает поля:

```json
"features": ["ai_drafts", "ai_continuations", "ai_import"],
"ai_consent_at": "2026-10-18T09:00:00Z"
```

`features` — функции **плана**, независимо от согласия: клиент показывает точки входа по `features`, а согласие запрашивает сам, видя `ai_consent_at: null`.

Название плана и срок клиенту **не отдаются**: приложению сейчас нечего показывать о подписке, а клиенту достаточно списка функций. Поля `plan`/`plan_expires_at` добавятся в контракт вместе с экраном покупки.

Изменение плана (выдача, отзыв) увеличивает `users.version` и пишет `SyncEntityType.User` в `ChangeJournal` — устройства получают новый `features` через sync/SSE без перезапуска. Истечение срока **не** порождает изменения в sync; клиент узнаёт о нём при следующем `GET /me` или по `403 feature_not_available`.

### Выдача плана

Команда приложения (как `migrate`, через `NodusApplication.TryRunCommandAsync`), без HTTP-эндпоинта — меньше поверхности атаки:

```bash
dotnet Nodus.Api.dll plan set --email user@example.com --plan plus [--expires 2027-01-01T00:00:00Z]
dotnet Nodus.Api.dll plan set --user-id <uuid> --plan standard
dotnet Nodus.Api.dll plan list
```

В контейнере: `docker compose run --rm nodus-api plan set …`. Команда меняет план в транзакции через `UnitOfWork` с записью в `ChangeJournal`, пишет `plan_source = manual`, логирует только `user_id` и план (без email). Выдавать стоит аккаунтам с привязанным email: анонимный аккаунт теряется при переустановке.

### Наблюдаемость

Счётчик `nodus_feature_denied_total{feature, reason}` (`reason`: `not_in_plan` | `consent_required`). Неявные отказы «Продолжения нити» в счётчик не попадают — это не действия пользователя.

## Рассмотренные варианты

1. **Ничего не делать / глобальные флаги в конфигурации.** Включает функцию сразу всем или никому; не решает задачу.
2. **Список пользователей в конфигурации** (`Features:AiDrafts:UserIds`). Просто, но выдача требует редеплоя, клиент не узнаёт об изменении через sync, нет пути к платному плану.
3. **Флаги функций на пользователя** (таблица `user_features(user_id, feature)`). Максимально гибко, но это не модель продукта: продаётся план, а не отдельные функции; выдача Nodus+ — три записи вместо одной. Можно добавить позже как overrides поверх плана, если понадобятся точечные исключения.
4. **План в `users` + функции плана в конфигурации** — выбран: соответствует продуктовой модели (обычный / Nodus+), одна точка выдачи, путь к StoreKit не меняет проверок.
5. **Внешний сервис флагов (LaunchDarkly, Unleash).** Лишняя зависимость и передача идентификаторов пользователей третьей стороне ради двух планов.

## Последствия

**Плюсы.** Одна проверка для всех AI-функций; неявная функция закрыта в фоне, а не только в UI; переход на платный Nodus+ сводится к новому источнику `plan_source = app_store` (проверка чеков / App Store Server Notifications) без изменения проверок и контракта `features`.

**Минусы.** Набор функций плана в конфигурации одинаков для всех экземпляров — при раскатке на долю пользователей понадобятся overrides (вариант 3). Истечение срока не приходит в sync сразу.

**Открытые вопросы (до релиза).**

- ~~**Вход ревьюера Apple.**~~ Решено: фиксированный код `EmailOtp:ReviewCode` для адресов `EmailOtp:ReviewEmails`, включается только на время ревью — [02 → Демо-аккаунт для App Review](../02-authentication.md#демо-аккаунт-для-app-review).
- Текст экрана согласия и пункт privacy policy об AI-провайдерах (какие провайдеры, что передаётся, срок хранения: `Ai:InputRetentionHours`) — продуктовая и юридическая часть, вне этого решения.

**Пересмотреть**, когда: появится оплата через App Store (таблица транзакций, `plan_source = app_store`, поля `plan`/`plan_expires_at` в контракте); понадобится раскатка на процент пользователей или исключения для отдельных людей (overrides); лимиты должны различаться по планам (`Ai:MaxJobsPerDay` → в `Plans:*`).

## Требования к iOS

1. **Источник доступа — `user.features`** из `GET /v1/me` и сущности `user` в sync. Хранить в локальном профиле; обновлять при каждом upsert `user` из sync. Если поля нет (старый сервер) — считать `[]`.
2. **Недоступные функции не показываются вовсе**, без замков, бейджей, упоминаний Nodus+, подписки или «скоро»:
   - нет `ai_drafts` — нет кнопки диктовки/AI-ввода и раздела «Черновики» (если в нём нет незавершённых заданий);
   - нет `ai_continuations` — ничего не меняется в UI; уже пришедшие предложения показываются как обычно;
   - нет `ai_import` — импорт принимает только файлы Nodus: в выборе файла и тексте экрана нет упоминания файлов других приложений.
3. **Потеря доступа не ломает начатое.** Задания черновиков и импорта в статусах `queued`/`processing`/`ready` остаются видимыми, их можно подтвердить или отменить; предложения продолжения показываются и принимаются.
4. **`403 feature_not_available`** (поле `feature` — ключ функции):
   - запрос **не повторять**, операцию удалить из Outbox (это не временная ошибка);
   - запросить `GET /v1/me`, обновить `features`, скрыть точку входа;
   - показать нейтральное сообщение: «Эта функция сейчас недоступна». Без слов «подписка», «Nodus+», «тестирование».
5. **Появление доступа** (функция пришла в `features` через sync/SSE) — точка входа появляется сразу, без перезапуска.
6. **Согласие на AI** (Guideline 5.1.2(i)). Источник истины — `user.ai_consent_at` с сервера, не локальный флаг.
   - Если в `features` есть хотя бы одна функция, а `ai_consent_at = null`, при первом обращении к AI-точке входа (диктовка, AI-импорт) показать экран: какие данные и кому отправляются, зачем, ссылка на privacy policy; кнопки «Разрешить» / «Не сейчас».
   - «Разрешить» → `PUT /v1/me/ai-consent { "granted": true }` через Outbox, затем запуск функции. «Не сейчас» → функция не запускается, экран покажется при следующей попытке.
   - Для `ai_continuations` отдельной точки входа нет: если у пользователя есть только эта функция, экран согласия показывается один раз ненавязчиво (например, после создания первого одноразового узла); отказ запоминается локально, чтобы не спрашивать снова, а в настройках остаётся переключатель.
   - В настройках — переключатель «AI-помощник» (виден, только если `features` не пуст) с текстом о передаче данных; выключение → `PUT /v1/me/ai-consent { "granted": false }`.
   - `403 ai_consent_required` (согласие отозвано с другого устройства) — обновить профиль и показать экран согласия, запрос не повторять автоматически.
7. **App Review:** в App Review Notes — текст об ограниченном тестировании AI-функций и данные демо-аккаунта с Nodus+; ревьюер входит через «Настройки → Восстановить аккаунт» с фиксированным кодом.
8. **Тесты приёмки:** пользователь без функций не видит ни одной AI-точки входа и экрана согласия; выдача плана на сервере открывает функции на устройстве без перезапуска; отзыв — скрывает, а незавершённые задания остаются доступны; `403 feature_not_available` не повторяется и скрывает точку входа; без согласия ни одна AI-функция не запускается, согласие и отзыв синхронизируются между устройствами.
