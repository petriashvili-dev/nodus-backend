# Outbox и обработка ошибок

Серверная сторона — [../04-sync-and-idempotency.md](../04-sync-and-idempotency.md).

## Модель операции

| Поле | Назначение |
|---|---|
| `id` | локальный id операции |
| `idempotency_key` | UUID, генерируется **при постановке** в очередь и не меняется никогда |
| `method`, `path`, `body` | готовый запрос; тело после постановки **не менять** |
| `entity_id` | узел/связь/задание, к которому относится операция (для порядка) |
| `depends_on` | операции, которые должны завершиться раньше |
| `status` | `pending`, `inFlight`, `retryableFailure`, `blockedConflict`, `failed`, `done` |
| `attempts`, `next_attempt_at`, `last_error_code` | backoff и диагностика |

Создание локальной сущности и запись операции — **одна транзакция** локальной БД. При старте приложения операции `inFlight` вернуть в `pending` и отправить повторно с тем же ключом — сервер не выполнит их дважды.

## Отправка

- Операции одного `entity_id` — строго по порядку, по одной. Независимые сущности — параллельно (2–4 одновременно).
- Создание узла → его правка/развязывание: правка зависит от создания (`depends_on`).
- Backoff: экспоненциальный с jitter (1 с, 2, 4… до 5 мин), без постоянного polling; при восстановлении сети и возврате в foreground — попытка сразу.
- После успешной отправки пачки — Delta Sync.

### `expected_version` в цепочке своих правок

`PATCH` узла требует `expected_version` — версию, на которой основана правка. Если офлайн сделано несколько правок одного узла:

- первая отправляется с версией, которую пользователь видел;
- каждая следующая — с `version` из ответа на предыдущую **свою** операцию по этому узлу.

Иначе сервер примет вторую собственную правку за конфликт. Поэтому `expected_version` вычисляется **при первой отправке** операции (когда предыдущая операция по узлу уже завершилась) и сохраняется в теле. Все повторы этой операции отправляют то же тело: сервер сравнивает хеш запроса, и изменённое тело с тем же ключом получит `422`.

Практичнее: несколько офлайн-правок одного узла **схлопывать** в одну операцию с последним состоянием (пока операция `pending`, а не `inFlight`).

## Ответы и что с ними делать

Сервер сохраняет **любой** ответ операции, включая 4xx: повтор с тем же ключом вернёт тот же ответ. Поэтому после бизнес-ошибки «попробовать ещё раз» = **новая** операция с **новым** ключом.

| Ответ | Статус операции | Действие |
|---|---|---|
| 2xx | `done` | применить каноническое состояние из ответа, снять pending-overlay |
| сеть / таймаут / нет ответа | `retryableFailure` | повтор с тем же ключом |
| 5xx, `500 internal_error` | `retryableFailure` | повтор с тем же ключом |
| `429 rate_limited`, `429 ai_quota_exceeded` | `retryableFailure` / `failed` | rate limit — повтор позже; квота AI — сообщить пользователю |
| `401 unauthorized` | — | refresh токена (single-flight), затем повтор с тем же ключом |
| `409 version_conflict` | `blockedConflict` | см. [ниже](#конфликт-версий) |
| `409 conflict` | `failed` | гонка на сервере: Delta Sync, затем при необходимости новая операция с новым ключом |
| `409 node_already_exists` | `done`* | *если узел с этим id уже есть у пользователя после sync — считать выполненным; иначе (коллизия id, практически невозможна) — новый id |
| `404 not_found`, `404 occurrence_not_found` | `failed` | узел удалён, доступ потерян или экземпляра больше нет (правило изменилось) — откатить локальное изменение, Delta Sync |
| `403 forbidden` | `failed` | действие не разрешено роли (участник не владелец) — откатить, показать |
| `400 validation_failed` | `failed` | ошибка клиента/данных: откатить или оставить черновик, показать `errors` |
| `422 idempotency_key_reused` | `failed` | баг клиента: тело операции изменилось при том же ключе. Залогировать, создать новую операцию |
| `400 idempotency_key_required` | `failed` | баг клиента |

Ответ с заголовком `Idempotent-Replayed: true` — повтор уже выполненной операции, обрабатывается как обычный ответ.

## Конфликт версий

```json
409 { "code": "version_conflict", "current": { …NodeDto… } }
```

1. Применить `current` как каноническое состояние узла.
2. Сохранить локальное намерение пользователя (поля его правки) в операции со статусом `blockedConflict`.
3. Разрешить:
   - правка не пересекается с изменениями `current` (разные поля) — автоматически создать **новую** операцию `PATCH` с `expected_version = current.version` и объединённым шаблоном;
   - пересекается (особенно в совместных узлах) — показать пользователю «Узел изменили: оставить моё / оставить их», затем новая операция или отмена.
4. Молча перезаписывать чужие изменения нельзя.

`409 version_conflict` без `current` (гонка на уровне БД) — Delta Sync и повтор новой операцией.

Развязать/перевязать конфликтов не дают: побеждает последнее действие.

## Офлайн-развязывание

`PUT /v1/nodes/{id}/occurrences/{key}/untie { "completed_at": "<момент действия>" }` — передавать реальное время действия; сервер примет его, если оно не в будущем и не старше 30 дней.

## UI для pending/ошибок

- Pending-операции не блокируют ленту и не требуют спиннера на каждой карточке; достаточно ненавязчивого индикатора «синхронизация».
- `failed` / `blockedConflict` — видимый статус на карточке и общий список «Не удалось синхронизировать» с действиями «Повторить» (новая операция) / «Отменить».
