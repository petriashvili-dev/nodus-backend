# Sync Engine и SSE

Серверная сторона — [../04-sync-and-idempotency.md](../04-sync-and-idempotency.md), [../05-realtime-and-push.md](../05-realtime-and-push.md).

## Когда синхронизироваться

- запуск приложения и возврат в foreground;
- восстановление сети (`NWPathMonitor` — только подсказка);
- после успешной отправки Outbox;
- сигнал SSE `sync.required`, любой push;
- смена календарного дня и часового пояса ([04](04-feed-occurrences-notifications.md)).

Одновременно — один цикл синхронизации; новые триггеры во время цикла объединяются в один следующий.

## Цикл

1. Отправить pending Outbox ([02](02-outbox-and-errors.md)).
2. `GET /v1/sync?cursor=<cursor>&limit=500`.
3. В **одной транзакции** локальной БД применить `changes` и сохранить `next_cursor`.
4. Повторять, пока `has_more = true`.
5. Перестроить ленту и план локальных уведомлений для затронутых узлов.

Первый запуск (курсора нет) — [snapshot](#snapshot).

```json
{
  "changes": [
    { "revision": 43, "entity_type": "node", "entity_id": "…", "operation": "upsert", "version": 5, "data": { … } },
    { "revision": 44, "entity_type": "occurrence_state", "entity_id": "<nodeId>:g0-20261018-0", "operation": "upsert", "version": 2, "data": { … } },
    { "revision": 45, "entity_type": "node", "entity_id": "…", "operation": "delete", "version": 6, "data": null }
  ],
  "next_cursor": 45,
  "has_more": false
}
```

## Применение изменений

Каждая сущность в странице встречается один раз, с актуальным состоянием. Применять по порядку `revision`.

| `entity_type` | `upsert` (`data`) | `delete` |
|---|---|---|
| `user` | профиль | — |
| `node` | `NodeDto` (с участниками и экземплярами на горизонт) — заменить серверный снимок узла и его экземпляры в окне `horizon` | удалить узел, его экземпляры, состояния, запланированные уведомления |
| `occurrence_state` | состояние экземпляра (`entity_id` = `{nodeId}:{key}`) | — |
| `connection` | связь с точки зрения пользователя | удалить связь |
| `ai_draft_job` | AI-задание с черновиками | удалить |
| `suggestion` | предложение продолжения | удалить (устарело) |
| `import_job` | AI-импорт | удалить |

`delete` приходит и тогда, когда сущность не удалена, а стала **недоступна** (вас убрали из совместного узла, связь разорвана). Неизвестный `entity_type` — пропустить (совместимость с будущими версиями сервера).

Локальные pending-изменения (overlay поверх серверного снимка) при применении sync не терять: серверный снимок обновляется, overlay остаётся, пока его операция не завершится.

## Snapshot

Нужен при первом запуске, после восстановления аккаунта и когда курсор устарел:

```json
410 { "code": "cursor_expired", "snapshot_url": "/v1/sync/snapshot" }
```

```http
GET /v1/sync/snapshot
→ { "cursor": 1234, "user": {…}, "nodes": […], "connections": […],
    "ai_draft_jobs": […], "suggestions": […], "occurrence_states": […] }
```

Заменить локальные серверные данные содержимым snapshot и сохранить `cursor` — в одной транзакции, **не трогая** Outbox и pending-overlay. Затем обычный цикл с этого курсора. Журнал на сервере хранится 90 дней: устройство, не синхронизировавшееся дольше, получит `410`.

## SSE

```http
GET /v1/events
Authorization: Bearer …
Last-Event-ID: <текущий локальный cursor>
Accept: text/event-stream
```

- Держать соединение только в foreground (`URLSession.bytes(for:)`).
- В `Last-Event-ID` передавать **текущий курсор синхронизации**: `id` события — это ревизия пользователя, поэтому если клиент отстал, сервер сразу пришлёт сигнал.
- События:
  ```
  id: 45
  event: sync.required
  data: {"revision":45,"event_id":"45"}
  ```
  и комментарии `: ping` каждые 20 с. Строки с `retry:` задают задержку переподключения (3 с).
- На `sync.required` — запустить цикл синхронизации (если `revision` > локального курсора). Данные из события **не применять**.
- Разрыв: переподключение с backoff (3 с → … → 60 с) и **всегда** цикл синхронизации после переподключения. `401` при подключении — refresh токена.
- При уходе в background — закрыть соединение; при возврате — синхронизация + новое подключение.
